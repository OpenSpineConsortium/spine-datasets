Which sets on the grid hold the same scans is measured by tools/lineage.py, queued by the gate word freeze overlap as one read-only job; its counts come back as lineage/OVERLAP.json through freeze report.

The owner asked on 2026-10-24 to remove sets for more useful ones under the oschome cap without losing any, one patient once across sets, and chose that day to build the ledger and run it as one job. The job reads every frozen set's FROZEN.files.tsv.gz and the header of up to three DICOM files per folder, never an image's pixels, and writes only into spine-datasets-freeze/lineage: lineage.sqlite, the per-file ledger with name stems and DICOM patient, study and series, which stays on the grid, and OVERLAP.json, counts alone per set and per pair (same bytes, shared series and study UIDs, patient IDs, identifier-like names, names that are another set's UIDs), held to that by public_problems. UIDs are proof of the same scan, hashes of the same bytes, names and patient IDs only leads. The design and the retirement plan are docs/research/lineage-and-retirement.md.

The first run (job 40775283, 98 sets) found no pair sharing anything it can see. Re-encoded NIfTI releases such as CTSpine1K and CTSpinoPelvic1K share no bytes and carry no UIDs, so that result does not show they hold different patients. Seeing that needs the sets' mapping files or a voxel fingerprint per volume, which is a heavier job and needs the owner's word.
